# Skill: dev-docs

**适用场景**：编辑、维护项目 `Docs/` 目录下的技术文档、设计文档、功能文档等。

**关联技能**：调用此技能时，必须一同读取 `obsidian` 技能，以确保文档格式符合 Obsidian 规范。

---

## 核心原则

### 1. 序号禁止规范（强制执行）

**核心原则：除非绝对必要，否则禁止使用任何形式的序号。**

#### 1.1 标题中禁止序号

**禁止在标题文字中包含任何形式的序号前缀或编号。**

| 错误示例（禁止） | 正确示例（必须改为） |
|-----------------|---------------------|
| `# 2.1 大厅整体设定` | `# 大厅整体设定` |
| `## 3.2.1 功能说明` | `## 功能说明` |
| `### 1. 概述` | `### 概述` |
| `#### 2.3 设计目标` | `#### 设计目标` |

**处理规则：**
- 删除标题开头的所有序号（如 `1.` `2.1` `3.2.1` 等）
- 删除标题中的编号前缀（如 `第一章` `第二节` 等，除非是正式出版物引用）
- 保留标题语义，仅移除序号

#### 1.2 目录名禁止序号

**禁止在目录/文件夹名称中使用序号前缀。**

| 错误示例（禁止） | 正确示例（必须改为） |
|-----------------|---------------------|
| `01-设计核心目标/` | `设计核心目标/` |
| `02-多人大厅系统/` | `多人大厅系统/` |
| `03-社交系统/` | `社交系统/` |
| `1-基础概念/` | `基础概念/` |
| `2-高级用法/` | `高级用法/` |

**处理规则：**
- 删除目录名开头的所有数字前缀（如 `01-` `02-` `1-` 等）
- 保留连字符 `-` 后的语义部分
- 如需排序，使用字母顺序或语义分组

#### 1.3 列表项禁止序号

**禁止在列表中使用序号，除非表示严格的操作步骤顺序。**

| 场景 | 正确做法 | 错误做法 |
|------|----------|----------|
| 功能列表 | `- 用户管理`<br>`- 权限控制` | `1. 用户管理`<br>`2. 权限控制` |
| 特性说明 | `- 支持多人在线`<br>`- 实时同步` | `1. 支持多人在线`<br>`2. 实时同步` |
| 文件清单 | `- README.md`<br>`- SKILL.md` | `1. README.md`<br>`2. SKILL.md` |
| **操作步骤**（唯一允许序号的场景） | `1. 打开设置`<br>`2. 点击保存`<br>`3. 确认退出` | （此场景必须用序号） |

**判断标准：**
- ✅ 使用序号：步骤之间有严格先后顺序，顺序错误会导致操作失败
- ❌ 禁止序号：条目之间是并列关系、列举关系、无顺序要求

#### 1.4 示例对比

**正确示例：**
```markdown
# 社交系统设计

## 核心功能
- 好友管理
- 私聊系统
- 群组功能

## 技术架构
- 前端：React
- 后端：Node.js
- 数据库：PostgreSQL
```

**错误示例（禁止出现）：**
```markdown
# 1. 社交系统设计

## 2.1 核心功能
1. 好友管理
2. 私聊系统
3. 群组功能

## 2.2 技术架构
1. 前端：React
2. 后端：Node.js
3. 数据库：PostgreSQL
```

### 2. 标题层级规范

- 使用标准 Markdown 标题语法：`#` `##` `###` `####`
- 禁止跳过层级（如从 `#` 直接到 `###`）
- 每个文档只有一个 `#` 一级标题
- 标题文字前后不留空格

### 3. 内容完整性

- 仅修改格式，不改变原文表达意思
- 不删除原文内容（除非明显为占位符或待删除标记）
- 不添加原文没有的内容（除非用户明确要求）
- 保持专业术语一致性

### 4. 格式统一（Obsidian 风格优先）

**核心原则：所有文档默认采用 Obsidian 风格格式，除非项目明确要求其他格式。**

| 元素 | 规范 |
|------|------|
| 代码块 | 使用三反引号 + 语言标识 |
| 行内代码 | 使用单反引号 |
| 强调内容 | 使用 `**粗体**` |
| 引用 | 使用 `>` 符号 |
| 表格 | 使用标准 Markdown 表格语法 |
| 外部链接 | 使用 `[文字](URL)` 格式 |
| **内部文档关联** | **必须**使用 `[[文档名]]` Wikilink 格式（Obsidian 原生支持） |
| **标签系统** | 使用 `#标签` 格式在文档末尾添加标签（如 `#VR` `#设计文档` `#多人系统`） |
| **Callouts** | 使用 Obsidian Callout 语法标注重要信息（如 `> [!NOTE]`、`> [!WARNING]`） |

### 5. 文档关联规范（Obsidian 风格）

**核心原则：相关文档之间建立双向链接，使用 Obsidian 原生 Wikilink 格式。**

#### 5.1 Wikilink 格式

- **语法**：`[[文档名]]`
- **文档名**：使用文档的文件名（不含 `.md` 后缀）
- **位置**：通常在文档末尾添加"相关文档"章节
- **别名**：支持 `[[文档名 | 显示文字]]` 格式

#### 5.2 示例

**正确示例：**
```markdown
# 社交系统设计

## 核心功能
- 好友管理
- 私聊系统
- 群组功能

## 相关文档
- [[道友系统]]
- [[仇道系统]]
- [[师徒系统]]
```

#### 5.3 关联规则

| 场景 | 操作 |
|------|------|
| 编辑文档 A 时提到文档 B | 在文档 A 末尾添加 `[[文档 B]]` |
| 文档 B 被其他文档引用 | 在文档 B 末尾添加"反向链接"章节，列出所有引用它的文档 |
| 发现文档之间有逻辑关联 | 主动建立双向链接 |

#### 5.4 自动关联建议

当编辑文档时，如果发现以下内容，应添加关联：
- 提到其他文档的核心概念
- 引用其他文档定义的系统
- 与其他文档描述的功能有交互关系

### 6. 标签规范（Obsidian 风格）

**核心原则：每个文档应在末尾添加标签，便于分类和检索。**

#### 6.1 标签格式

- **语法**：`#标签名`
- **位置**：文档末尾，单独一行
- **层级**：支持 `#父标签/子标签` 格式（如 `#系统/社交`）
- **数量**：建议 3-5 个标签，覆盖核心主题

#### 6.2 示例

```markdown
---
tags: [VR, 设计文档，多人系统]
---

# 社交系统设计

## 核心功能
- 好友管理
- 私聊系统
- 群组功能

## 相关文档
- [[道友系统]]
- [[仇道系统]]

#VR #设计文档 #多人系统/社交 #后端架构
```

#### 6.3 推荐标签体系

| 类别 | 标签示例 |
|------|---------|
| 项目类型 | `#VR` `#Android` `#PICO` |
| 文档类型 | `#设计文档` `#技术规范` `#会议纪要` `#功能说明` |
| 系统模块 | `#多人系统` `#社交系统` `#渲染系统` `#交互系统` |
| 技术栈 | `#URP` `#OpenXR` `#InputSystem` `#ShaderGraph` |

### 7. Callout 标注规范（Obsidian 风格）

**核心原则：使用 Obsidian Callout 语法突出重要信息、警告、提示等。**

#### 7.1 Callout 类型

| 类型 | 语法 | 用途 |
|------|------|------|
| 注意 | `> [!NOTE]` | 一般提示信息 |
| 提示 | `> [!TIP]` | 建议、技巧 |
| 重要 | `> [!IMPORTANT]` | 关键信息 |
| 警告 | `> [!WARNING]` | 需要注意的风险 |
| 错误 | `> [!ERROR]` | 错误信息、禁止事项 |

#### 7.2 示例

```markdown
> [!NOTE] 性能提示
> SpaceWarp 仅在 PICO 4 上支持，Quest 2 需要降级方案。

> [!WARNING] breaking change
> 修改 XR 配置后必须重新构建项目，热重载不生效。

> [!IMPORTANT] 必须先完成
> 在开始多人功能开发前，确保已配置 PICO Platform SDK。
```

### 8. 文件命名规范

- 使用小写字母、数字、连字符 `-`
- 中文文件名保持语义清晰
- 避免使用空格和特殊字符
- 示例：`user-auth-flow.md` 或 `用户认证流程.md`

### 9. 目录结构建议（Obsidian 风格）

#### 9.1 基础目录结构

```
Docs/
├── 功能/           # 功能设计文档（代码相关功能）
├── 技术/           # 技术架构文档
├── 规范/           # 开发规范文档
├── 会议/           # 会议纪要
├── 外部/           # 外部参考资料
└── MOCs/           # Map of Content - 索引文档
    ├── 索引.md
    ├── 功能索引.md
    └── 技术索引.md
```

#### 9.2 功能目录结构（代码相关功能）

所有代码相关功能必须放在 `功能/` 目录下，按以下四级分类组织：

```
Docs/
└── 功能/
    ├── 框架/           # 框架级模块（系统级、跨应用）
    │   └── {框架名}/
    │       ├── 配置.md
    │       ├── 示例.md
    │       └── API.md
    ├── 组件/           # 组件级模块（可复用组件）
    │   └── {组件名}/
    │       ├── 配置.md
    │       ├── 示例.md
    │       └── API.md
    ├── 模块/           # 功能模块（具体业务功能）
    │   └── {模块名}/
    │       ├── 配置.md
    │       ├── 示例.md
    │       └── API.md
    └── 任务步骤/       # 任务步骤（工作流、操作流程）
        └── {任务名}/
            ├── 配置.md
            ├── 示例.md
            └── API.md
```

**分类定义：**

| 分类 | 说明 | 示例 |
|------|------|------|
| **框架** | 系统级、跨应用的底层框架 | 网络同步框架、输入系统框架、音频管理框架 |
| **组件** | 可复用的独立组件 | 按钮组件、滑动条组件、血条组件 |
| **模块** | 具体业务功能模块 | 登录模块、商店模块、好友系统 |
| **任务步骤** | 操作流程、工作流步骤 | 场景切换流程、新手引导步骤 |

**MOC（Map of Content）规范：**
- 每个主要分类应有对应的 MOC 文档
- MOC 文档列出该分类下所有模块的 `[[Wikilink]]`
- MOC 文档本身也应被其他 MOC 引用，形成知识网络

### 10. 模块文档三文件规范

每个模块必须包含三个文件：配置.md、示例.md、API.md。

#### 10.1 配置.md（Configuration）

**用途**：模块的配置信息、环境要求、依赖关系

**必须包含内容**：
- 模块概述
- 环境要求（Unity版本、SDK版本等）
- 依赖项列表
- Inspector配置字段说明
- 配置文件格式
- 性能参数建议

**示例结构**：
```markdown
# 网络系统配置

## 环境要求
- Unity 2022.3+
- Netcode for GameObjects 2.x

## 依赖项
- [[UniTask]]
- [[PICO XR SDK]]

## Inspector配置
| 字段 | 类型 | 说明 |
|------|------|------|
| `serverAddress` | string | 服务器地址 |

#网络 #配置
```

#### 10.2 示例.md（Examples）

**用途**：使用示例、代码片段、操作步骤

**必须包含内容**：
- 快速开始示例
- 典型使用场景
- 代码示例（带注释）
- 步骤教程（如需）
- 注意事项

**示例结构**：
```markdown
# 网络系统示例

## 快速开始
```csharp
var manager = new NetworkManager();
manager.Connect("192.168.1.100", 12000);
```

## 典型场景
### 场景1：主机模式启动
...

#网络 #示例
```

#### 10.3 API.md（API Reference）

**用途**：接口定义、方法签名、参数说明

**必须包含内容**：
- 类/接口定义
- 方法列表（含参数、返回值）
- 事件/委托定义
- 类型定义
- 版本变更记录

**示例结构**：
```markdown
# 网络系统API

## NetworkManager类

### Connect方法
```csharp
public async UniTask<bool> Connect(string ip, ushort port)
```

**参数**
| 参数 | 类型 | 说明 |
|------|------|------|
| ip | string | IP地址 |
| port | ushort | 端口号 |

**返回值**
- `true`：连接成功
- `false`：连接失败

#网络 #API
```

### 10.4 文件命名规范

- 每个模块一个文件夹，使用有意义的模块名
- 三个文件名固定为：`配置.md`、`示例.md`、`API.md`
- 模块文件夹命名示例：`网络系统/`、`音频管理器/`、`场景切换/`

### 10.5 完整示例

**网络系统模块的完整结构**：

```
Docs/
└── 功能/
    └── 模块/
        └── 网络系统/
            ├── 配置.md      # 环境要求、依赖、Inspector配置

            └── API.md       # 类定义、方法、参数
```

### 11. 迁移指南

#### 11.1 从旧结构迁移到新结构

**迁移步骤**：
1. 识别现有文档属于哪个分类（框架/组件/模块/任务步骤）
2. 创建对应的模块文件夹
3. 将原内容拆分到三个文件中
4. 更新 MOC 索引
5. 更新相关 Wikilink

**迁移示例**：

**迁移前**：
```
Docs/
└── 功能/
    └── 网络系统.md    # 单个文件，包含配置+示例+API
```

**迁移后**：
```
Docs/
└── 功能/
    └── 模块/
        └── 网络系统/
            ├── 配置.md    # 原文件中的配置部分
            ├── 示例.md    # 原文件中的示例部分
            └── API.md     # 原文件中的API部分
```

**内容拆分示例**：

原 `网络系统.md` 内容：
```markdown
# 网络系统

## 配置
需要 Netcode for GameObjects 2.x

## 示例
```csharp

## API

**配置.md**：

**示例.md**：

```csharp

**API.md**：
```markdown

#### 11.2 新模块创建流程

1. 确定模块分类（框架/组件/模块/任务步骤）
2. 创建模块文件夹：`Docs/功能/{分类}/{模块名}/`
3. 创建三个文件：`配置.md`、`示例.md`、`API.md`
4. 填写基础信息（frontmatter、概述）
5. 逐步完善各文件内容
6. 更新 MOC 索引
7. 建立相关 Wikilink

## 触发条件

当用户请求涉及以下操作时，自动应用本技能规范：

- 编辑 `Docs/` 目录下的 `.md` 文件
- 创建新的功能文档或设计文档
- 创建或编辑代码相关功能文档（必须放在 `Docs/功能/` 下，使用三文件结构）
- 整理、重构现有文档结构
- 统一文档格式风格
- 将现有文档迁移到新模块结构

## 快速决策指南

### 当用户要求创建文档时：

**Q: 这是什么类型的文档？**

- **代码相关功能**（类、组件、系统、框架）→ 使用 `Docs/功能/{分类}/{模块名}/` 三文件结构
- **技术架构**（架构设计、技术选型）→ 使用 `Docs/技术/` 目录
- **开发规范**（编码规范、命名规范）→ 使用 `Docs/规范/` 目录
- **会议纪要** → 使用 `Docs/会议/` 目录
- **外部资料** → 使用 `Docs/外部/` 目录

**Q: 代码相关功能如何分类？**

| 如果功能... | 放在... | 示例 |
|-------------|---------|------|
| 是系统级框架，跨应用使用 | `功能/框架/` | 网络同步框架、输入系统框架 |
| 是可复用的独立组件 | `功能/组件/` | UI按钮组件、血条组件 |
| 是具体业务功能模块 | `功能/模块/` | 登录模块、商店系统 |
| 是操作流程或工作流 | `功能/任务步骤/` | 场景切换流程、新手引导 |

**Q: 如何快速创建模块文档？**

```
1. 确定分类 → 框架/组件/模块/任务步骤
2. 创建文件夹 → Docs/功能/{分类}/{模块名}/
3. 创建三文件 → 配置.md + 示例.md + API.md
4. 填写基础 → frontmatter + 概述
5. 逐步完善 → 按文件类型填写内容
6. 建立关联 → Wikilink 链接相关文档
```
